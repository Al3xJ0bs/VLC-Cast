# VLC Cast v0.9.3 — самообновление в приложении + DASH + 12 одобренных фич

Android-приложение для Алексея: каст видео из браузера (YummyAnime и др.)
на Apple TV через VLC. **Шаринг в фоне, приложение не открывается:**
Chrome → Поделиться → VLC Cast → всё происходит в фоне, на экране
только уведомление «Отправляю видео на Apple TV…» → видео само
запускается во VLC на ТВ. Тап по иконке — **только экран-инструкция**
про шаринг ссылки, больше ничего. Прямой каст видео **не работает
на tvOS 27.2** — ТВ отклоняет любую вставку в очередь
(`POST /command` всегда HTTP 400, шесть сборок v0.3.0–v0.3.5) — и
**удалён в v0.5.2** по приказу Алексея (2026-11-18 00:41: убрать
нерабочие функции ненужного пути). Зеркало экрана **удалено в v0.6.0**
(«вообще не интересно», его слово 2026-11-10). Подробности истории —
в разделе «Прямой каст (v0.2.0–v0.3.5)» ниже и в
`research/direct-cast-research-2026-11-10.md`.

## v0.9.3 — самообновление, DASH, 60fps, проверка VLC, бэкап спаривания + два хотфикса 0.9.2 (2026-11-18)

Двенадцать одобренных Алексеем пунктов (нумерация из списка 27 предложений 2026-11-18) + два хотфикса по живому вердикту 0.9.2 (05:43: каст с сайтов РАБОТАЕТ, сломаны шаринг файла из Telegram и Instagram) + самообновление внутри приложения (его слово).

### 0. Хотфиксы 0.9.2

1. **Telegram-файл — тишина.** 0.9.2 откладывала старт сервиса до конца копии (фоновый поток + runOnUiThread); NoDisplay-activity без окна система прибивает раньше — `startForegroundService` из фона падает (`ForegroundServiceStartNotAllowedException`, Android 12+) и всё умирает молча. Тост «Копирую файл…» мелькал — ветка достигалась, смерть после старта копии. Фикс: **сервис стартует СИНХРОННО в `onCreate`, ДО копии** (как в 0.9.1 — путь доказано доходит до сервиса), уведомление «Копирую файл…» сразу; копия в фоне с таймаутом 60 с (`copySharedFileWithTimeout`); путь отдаётся уже работающему сервису вторым интентом (`ACTION_FILE_DELIVER`); копия не удалась/таймаут — fallback на URI + ошибка с «Поделиться логом». Весь старт и доставка — в try/catch с логом.
2. **Instagram — «Видео не найдено».** SCAN_JS ищет og:video/video_url, но Instagram отдаёт голому WebView страницу входа без og:video. Фикс: если WebView-скан не дал кандидатов — **прямой HTTP-fetch HTML с десктопным UA** (без WebView, `VideoUrls.extractMetaVideoUrls`: og:video / og:video:secure_url / og:video:url / twitter:player:stream / `"video_url"` из JSON) — для instagram.com в первую очередь, иначе со второго рескана; при третьем — десктопный UA в самом WebView (пункт 25).

### 1. Самообновление внутри приложения (слово Алексея)

Кнопка «Скачать» → **«Скачать и установить»**: DownloadManager с видимым прогрессом в уведомлении, файл — `getExternalFilesDir(Download)/VLC-Cast-update.apk`, без лишних разрешений; по завершении — автоматический промпт установки (ACTION_VIEW + FileProvider, `application/vnd.android.package-archive`). Manifest: `REQUEST_INSTALL_PACKAGES`; перед скачиванием `canRequestPackageInstalls()` — если нет, один раз в `Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES` с объяснением, после возврата скачивание продолжается само. **Честно: подпись проверяет сам Android при установке поверх (тот же keystore) — чужой APK просто не встанет.** Старый APK чистится при следующем запуске / перед следующим скачиванием (у ACTION_VIEW-промпта нет callback о завершении установки — удалить сразу после промпта нельзя честно). Источник — тот же `latest.json` (публичный репозиторий, см. ниже); кнопка «Скачать и установить» — только когда есть новая версия.

### 2. Пункты 1, 4, 5, 14, 17, 18, 20, 23, 24, 25, 26, 27

- **1. DASH из раздельных дорожек:** `DashManifest.build` синтезирует локальный .mpd (два AdaptationSet + SegmentBase, initRange обязателен — без него VLC не найдёт moov), прокси отдаёт его по `/dash.mpd?id=…` (`StreamProxy.registerDash`), сегменты VLC качает напрямую с googlevideo. Пока только YouTube adaptive (видео-only + аудио-only из одного /player-ответа, `pickDashPair`); generic pairing страниц не делается — надёжного сигнала спаривания нет. Приоритет: HLS/muxed/audio-only выше, DASH — только когда их нет.
- **4. 60fps:** `VideoCandidate.fps`, `VideoUrls.fpsOf` (по `60fps`/`p60` в URL); `orderedAttempts` — fps как tie-break внутри равного score (формат+качество), не выше.
- **5. Проба скорости зеркал:** перед запуском — конкурентный замер первого байта (Range 0-0) в tied top-score группе (равный score, ≥2 хостов), дедлайн 2,5 с; нет данных — исходный порядок. Прокси-URL не пробуются (один хост — телефон).
- **14. Проверка VLC:** перед запуском — `CompanionClient.fetchLaunchableApps` (`FetchLaunchableApplicationsEvent`, `_c` = `{bundle_id: name}`); нет VLC — честная ошибка «VLC не установлен на Apple TV — установи VLC из App Store», а не тишина. Не удалось проверить (нет спаривания/сеть) — fail-open, запуск как обычно. Один лишний Companion-коннект на флоу.
- **17. Куки + вход:** `CookieManager.flush()` после каждой загрузки страницы (логин через fallback видимый браузер сохраняется); куки/Referer — в прокси и pre-flight (как раньше); кнопка «Сохранить вход (куки)» в фолбэке — ручной flush + тост.
- **18. Самопроверка при первом запуске:** блок на экране-инструкции + кнопка «Проверить»; авто — один раз на версию (`selfcheck_done_for`). Три состояния (✓/✗/?): ТВ доступен (TCP 7000), спарен, VLC установлен (app_list, UNKNOWN без спаривания). Результат сохраняется (`selfcheck_last_result`).
- **20. «Что нового»:** карточка на экране-инструкции один раз на новую версию (`last_seen_version`), кнопка «Понятно» записывает версию.
- **23. JSON-LD VideoObject:** SCAN_JS собирает `script[type="application/ld+json"]` (+ same-origin iframe); `parseJsonLdVideoObject` — contentUrl (только видео-URL) или embedUrl (только видео-URL); `@graph` — regex по всему блоку; contentUrl-массив не поддерживается (в разметке почти всегда строка).
- **24. oEmbed:** SCAN_JS собирает `link[rel="alternate"][type="application/json+oembed"]` (только JSON); `parseOembedVideoUrl` — type=photo/link → null; type=video/без типа → `url` или iframe `src` из `html` (только видео-URL); fetch — 256 КБ, 8 с, один раз на ссылку за флоу.
- **25. Desktop UA:** если мобильный UA не дал видео — третий рескан перезагружает страницу с десктопным UA (Chrome 126) в том же WebView; при возврате к новому флоу — мобильный UA обратно. Дедлайн поиска 30 с не меняется.
- **26. Lazy-iframe:** при поиске после каждой загрузки страницы — `LAZY_IFRAME_JS`: `loading='eager'` + `scrollIntoView` для iframe, затем повторный скан. В видимом фолбэке страница может прыгнуть — только пока идёт поиск.
- **27. Бэкап спаривания:** экспорт Companion-учёток (HAP + companion) в `aircast-pairing-backup.txt` (share sheet через LogFileProvider) и импорт обратно — восстановление после переустановки без повторного PIN. Формат: `# VLC Cast pairing backup v1` + `identity<TAB>serialize()`. **Файл содержит секреты спаривания — хранить в надёжном месте и удалить после восстановления.** KeyStore-шифр для бэкапа не годится (ключ умирает с переустановкой) — экспортируется PLAINTEXT serialize().

**Не проверено вживую:** всё выше — только unit-тесты + мок Companion (7/7). Живая проверка — на телефоне Алексея: Telegram-файл, Instagram, самообновление (скачивание + промпт + установка поверх), DASH на YouTube, проба зеркал, проверка VLC, самопроверка, «Что нового», бэкап (экспорт → переустановка → импорт → каст без PIN).

## v0.9.2 — каст музыки + источник обновлений + два срочных бага 0.9.1 (2026-11-18)

### 1. Каст музыки (по слову Алексея 2026-11-18 03:54)

Та же механика, что у видео: шаринг ссылки → детект аудио →
Companion launch_app с `vlc-x-callback-url/stream`. Видео в
приоритете: если страница содержит и видео, и аудио — кастится
видео; аудио — только если видео нет.

- Прямые ссылки: `.mp3/.aac/.flac/.ogg/.m4a/.wav/.opus` (+ HLS-аудио
  `.m3u8` с аудио — SoundCloud `cf-hls-media.sndcdn.com`).
- Страницы/плееры: SoundCloud (media API `api-v2.soundcloud.com/media/…`
  резолвится в реальный `.m3u8`, `client_id` — из запроса самого
  плеера), YouTube Music (InnerTube, аудио-only itag 141/251/140…),
  интернет-радио (плейлисты `.pls/.m3u` → первый поток), Bandcamp
  (прямые mp3 из JSON страницы, `tN.bcbits.com/stream/…`).
- Локальные аудиофайлы: шаринг `audio/*` из галереи/файлового
  менеджера — тем же локальным HTTP-сервером, что видеофайлы
  (`/file` с Range, свои Content-Type `audio/mpeg`, `audio/flac`…),
  с обязательным автоудалением временной копии после каста (и при
  неудаче, и stale-cleanup при запуске сервиса). Оригинал не трогается.
- Обложка и название трека: VLC показывает метаданные аудио (ID3/ICY)
  сам — приложение отдаёт поток/файл с сохранёнными метаданными
  (прокси байты не меняет). **Честно: обложка/название появляются
  только если они есть в метаданных источника; где их нет — VLC
  покажет URL, как и у видео.**
- Длительность трека — для таймера конца/очереди: mp4/m4a — mvhd,
  mp3 — Xing/Info или CBR-оценка (для VBR врёт, честно — оценка).

**НЕ в скопе (явно): Spotify и Apple Music — потоки зашифрованы
(DRM), прямую ссылку вытащить нельзя и во VLC не сыграть.** При
шаринге такой ссылки — честная ошибка сразу, а не молчаливое
«не найдено». Обход DRM не делается.

**Честные ограничения музыки:** голые Icecast-URL вида `/stream`
без расширения не детектятся (нет маркера аудио); YouTube Music —
только InnerTube adaptive, `signatureCipher` не расшифровывается;
SoundCloud — только через перехват сети/JS-скан страницы (прямая
ссылка на трек без плеера не резолвится).

### 2. Источник обновлений по умолчанию (по слову Алексея)

Публичный репозиторий **Al3xJ0bs/VLC-Cast**, `latest.json` в корне
ветки `main`:
`https://raw.githubusercontent.com/Al3xJ0bs/VLC-Cast/main/latest.json`.
Проверка обновлений использует его без ручного ввода; в настройках
поле предзаполнено этим URL, пользователь может его изменить
(пустое поле = назад к умолчанию). Формат:
`{"versionCode":33,"versionName":"0.9.3","url":"https://github.com/Al3xJ0bs/VLC-Cast/releases/download/v0.9.3/VLC-Cast-0.9.3.apk"}`.
`latest.json` опубликован в репозитории (с v0.9.2); если файла нет
(404) — честно «источник обновлений недоступен», без падения
(код различает 404, ошибку сети и мусор в JSON). Старый честный
пробел «источник не задан» из v0.9.1 закрыт.

### 3. СРОЧНЫЙ БАГ 0.9.1: шаринг видеофайла из Telegram — «Не удалось открыть файл»

Причина: URI-permission от Telegram не доходит до сервиса (grant
на activity, а activity делает `finish()` сразу после
`startForegroundService`) — `openFileDescriptor`/`openInputStream`
в сервисе возвращали null, хотя `DISPLAY_NAME` в activity читался.
Фикс: **activity сама копирует файл в `cacheDir/aircast-temp`
(`TempFiles.tempName()`), пока grant жив**, в фоновом потоке, и
сервису отдаёт путь к копии (новый extra `EXTRA_FILE_PATH`,
`filePathCastIntent`); движок читает копию напрямую
(`JavaFileSource`), без `openFileDescriptor`. Старый путь через
content URI оставлен как fallback на случай ошибки копии.
Логируется каждый шаг (размер копии, класс исключения). Ошибка
файла — с действием «Поделиться логом» в уведомлении (как «Видео
не найдено»). Автоудаление копии — как раньше (после каста/при
неудаче + stale-cleanup). То же — для аудиофайлов из Telegram.

### 4. СРОЧНЫЙ БАГ 0.9.1: каст не шёл НИОТКУДА (три регрессии)

1. **TV pre-check (`ensureTvReady`) убивал каст без fallback.**
   Запомненный ТВ не отвечает на TCP-пробу 7000 → сразу
   `onTvUnreachable`, без mDNS (как было в 0.9.0). А `wakeTv()`
   через Companion спящий ТВ не будит: `connect()` на 49153 падает,
   пока ТВ спит. Фикс: при неудаче probe+wake — **обязательно
   fallback на mDNS** (`fallbackToDiscovery`: найти ТВ заново,
   обновить запомненный host, продолжить запуск); `onTvUnreachable`
   — только если и mDNS никого не нашёл (с drain очереди).
   В комментарии зафиксировано: wake через Companion работает
   только при живом Companion; спящий ТВ будится коннектом после
   mDNS (sleep proxy). Уведомление «Apple TV недоступен» — теперь
   с «Поделиться логом».
2. **Очередь: следующий шаринг вставал в очередь на часы.**
   После успешного запуска с неизвестной длительностью `armCapTimer`
   ставил таймер на 3 ч, а `isBusy()` считал движок занятым
   (`launched && nextTimerRunnable != null`). Фикс: `isBusy` —
   только пока идёт поиск/запуск (`SEARCHING_TV/LOADING_PAGE/
   SEARCHING_VIDEO/LAUNCHING`, чистая функция `isBusyState` для
   unit-тестов); когда видео уже запущено (`LAUNCHED`) — **новый
   шаринг ПРЕРЫВАЕТ текущий каст и запускается сразу** (поведение
   0.9.0). Cap-таймер 3 ч — только для авто-следующей/позиции.
3. **Терминальная ошибка оставляла движок зависшим.**
   После исчерпания попыток и Companion-исключения `flowState`
   оставался `SEARCHING_VIDEO` навсегда без таймера и без drain.
   Фикс: `failFlow` — `flowState=IDLE` + запуск следующего элемента
   очереди, если есть; уведомление слушателю — только если очередь
   пуста. Применяется к launch failed, onError, timeout, TV
   unreachable и ошибкам файлового флоу.

**Не проверено вживую:** музыка, обновление по умолчанию
(`latest.json` 32/0.9.2 опубликован в репозитории, релиз v0.9.2
есть — проверка доступна), исправления обоих багов — только
unit-тесты (410 PASS) + мок Companion 6/6. Живая проверка — на
телефоне Алексея.

## v0.9.1 — обновления, настройка, память, resume, плейлисты, очередь, файлы, Instagram, Twitch/Kick (2026-11-18)

Шестнадцать фич по решениям Алексея (2026-11-18 03:37–03:50), в порядке
приоритета. Всё детерминированно, без LLM в пути извлечения/
воспроизведения. Не сделано (его же слово): виджет, Infuse как
запасной плеер, «смотреть позже», таймкоды, автопауза при звонке,
кнопки громкости ТВ, карточка «продолжить просмотр», пульт
в уведомлении, таймер сна, Piped, выбор качества вручную
(остаётся автовыбор лучшего). История кастов — не решена, не входит.

### 1. Проверка обновлений — первая фича

- При запуске (не чаще раза в день) + кнопка «Проверить обновления»
  на экране-инструкции. Сравнивает versionCode с JSON по заданному
  URL: `{"version_code": N, "version_name": "...", "url": "..."}`.
  Если новее — экран/диалог с кнопкой «Скачать» (открывает URL).
- **Честно: источника по умолчанию НЕТ** — URL задаётся в настройках
  (поле «URL проверки обновлений», `update_check_url`). Без URL —
  честное «источник не задан», а не молчание и не ложная «последняя
  версия». Причина: у проекта нет публичного репозитория/хостинга
  версий (git-репозиторий локальный, remote нет) — проверять «из
  коробки» некуда. Когда появится источник (GitHub-релиз / файл
  на хостинге) — URL вписывается один раз в настройках.
  (v0.9.2: закрыто — источник по умолчанию появился: публичный
  репозиторий Al3xJ0bs/VLC-Cast, `latest.json` в ветке `main`,
  см. раздел 2 выше.)

### 2. Блок «Настройка один раз» + текст инструкции

- На экране-инструкции: «На Apple TV должен быть установлен VLC;
  один раз нужно найти приставку и спарить по PIN-коду». Кнопка
  «Спарить Apple TV» — пока ТВ не спарен (тот же флоу спаривания,
  что раньше был доступен только из уведомления); когда спарен —
  «ТВ спарен ✓». После спаривания блок перерисовывается сам.
- Текст инструкции: «Откройте страницу с видео в Chrome» →
  «в Chrome или другом приложении» (шаринг работает из любого
  приложения, не только Chrome).

### 3. Запоминать озвучку

- Ключ — сериал/источник (host + шаблон пути с номером серии,
  последний номер → `#`). При повторном касте того же сериала
  `orderedAttempts` предпочитает кандидата с той же audioLabel
  (метка `{Rus}`/`{Eng}` из Playerjs/плеера, +5 к счёту,
  `preferredDubForCurrent()`). Если такой дорожки в этот раз нет —
  автовыбор лучшего, как раньше. Запомненная озвучка ставится
  при успешном запуске (`rememberDubForCurrent`).

### 4. Продолжить с того же места (resume)

- Позиция запоминается по таймеру (см. ограничение ниже): при
  сбросе флоу / срабатывании таймера конца / уничтожении сервиса —
  elapsed − 15 с на старт, только если > 60 с и > 60 с до конца
  (`PlaybackMemory.isResumable`). Позиция — на видео/сериал.
- При повторном шаринге того же видео — **HLS**: прокси `/resume`
  обрезает плейлист до позиции (`ResumePlaylist.trim`: сегменты,
  целиком закончившиеся до позиции, выбрасываются; `#EXT-X-KEY` /
  `#EXT-X-MAP` сохраняются, `#EXT-X-MEDIA-SEQUENCE` и
  `#EXT-X-TARGETDURATION` пересчитываются, `#EXT-X-ENDLIST`
  сохраняется; точность — до сегмента, обычно 2–10 с). Таймер
  конца серии при этом идёт на оставшееся время.
- **mp4 — честное ограничение: resume нет**, запускается с начала
  (нет плейлиста, который можно обрезать).
- **Ограничение (главное): позиция — таймерная эвристика.**
  Companion состояния воспроизведения НЕ даёт вообще; честный
  MRP-клиент — отдельная большая работа, не в этом скоупе.
  Пауза/перемотка с пульта ТВ позицию собьёт.

### 5. Плейлисты YouTube

- Шаринг ссылки на плейлист (`list=…` / `youtube.com/playlist`):
  InnerTube `/browse` с тем же VISIONOS-клиентом
  (`browseId: "VL<id>"`, `YouTubePlaylist`) → первое видео кастится,
  остальные — в очередь (первая страница, до 100 видео, дубли
  убираются). Дальше — обычный флоу каста на каждое видео.

### 6. Название видео в уведомлении

- `TitleCleaner.parse`: срезать суффикс сайта (`| YummyAnime`),
  выкинуть мусор («смотреть онлайн», «дивитись онлайн»,
  «бесплатно», «в хорошем качестве», hd/720p/1080p), вытащить
  сезон/серию («1 сезон 5 серія», S02E05, `?ep=5`, `/s1e5/`).
  Уведомление об успехе: «Розаріо вампір — 1 сезон, 5 серия».
  Если чистое название не вытащилось — host/URL, без выдумывания.
- Та же чистка — для поиска субтитров (п. 13) и для имени файла
  (галерея/Telegram, `cleanFileName`).

### 7. Проверка ТВ заранее

- Перед детектом: TCP-проба запомненного ТВ (`TvCheck.probe`,
  порт 7000, 2 с). Недоступен → пробуждение (п. 10) → опрос
  до 30 с → если всё равно нет — сразу честное уведомление
  «Apple TV недоступен», а не 30-секундный молчаливый таймаут.
  ТВ не запомнен — прежний путь через mDNS-поиск.

### 8. Очередь шарингов

- Пока идёт поиск/загрузка/запуск или серия играет с вооружённым
  таймером — новый шаринг не перебивает текущий, а встаёт
  в очередь (`CastQueue`, FIFO). По окончании — следующий из
  очереди (`onPlaybackEnd` → queue → предзагруженная серия →
  авто-следующая). Уведомление показывает размер очереди.

### 9. Запоминать выбор субтитров

- Вкл/выкл + язык — на сериал/источник (`PlaybackMemory`).
  При следующем касте: запомнено «выкл» — субтитры не
  подставляются вообще; запомнен язык — он идёт первым в `sub=`
  и получает `DEFAULT=YES` в HLS-мастере (`buildSubsMaster`
  с `preferredLang`). Переключение — действием в уведомлении
  «Субтитры вкл/выкл» (`ACTION_TOGGLE_SUBS`, действует
  со следующего запуска).

### 10. Пробуждение ТВ перед кастом

- Companion `turn_on` (HID Wake: `_hidC` 13, `_hBtS` 2,
  `CompanionClient.wakeTv()`) — **НЕ Wake-on-LAN**: WoL по Wi-Fi
  на Apple TV ненадёжен (по Ethernet — да, по Wi-Fi — ограничен/
  не поддерживается на части моделей). После пробуждения —
  ожидание готовности до ~30 с. Если ТВ уже бодрствует —
  пробуждение не мешает.

### 11. Предзагрузка следующей серии

- Пока идёт текущая серия — тот же WebView в фоне (`preloadMode`)
  детектит URL потока следующей серии (дедлайн 30 с, без
  авто-запуска). К концу серии поток уже известен — переключение
  мгновенное (`launchPreloaded`). Best-effort: не успел за 30 с —
  обычный флоу детекта.

### 12. Постер в уведомлении «запущено»

- `og:image` со страницы (SCAN_JS, только верхний документ)
  скачивается один раз за флоу (до 2 МБ, `posterBytes`) и
  показывается в уведомлении `BigPictureStyle` вместе с чистым
  названием (`onLaunched` → через 10 с — уведомление «Серия идёт»,
  если вооружена авто-следующая).

### 13. Субтитры из внешних баз (OpenSubtitles) + парсинг названия

- OpenSubtitles API v1: поиск по чистому названию + сезон/серия
  (`GET /subtitles?query=&languages=&season_number=&episode_number=`),
  скачивание по временной ссылке (`POST /download`).
  Найденная дорожка — `.srt`/`.ass` → VTT (или `.vtt` как есть),
  регистрируется как `/memory-vtt` и подставляется в каст.
  Поиск — один раз за флоу, только если в странице нет своих
  дорожек и чистое название известно.
- **Честно: нужен бесплатный API-ключ consumer** (регистрация
  на opensubtitles.com, ключ вписывается в настройки — поле
  «Ключ OpenSubtitles», `opensubtitles_api_key`; REST v1 требует
  заголовок `Api-Key` даже для поиска). Без ключа — поиск
  пропускается с честной записью в лог, приложение работает
  как раньше. Точность поиска — по названию, без moviehash
  (файла нет — стрим).

### 14. Шаринг видеофайлов (Telegram, галерея)

- `ACTION_SEND` с video/*: `content://` URI уходит в сервис
  (data URI + `FLAG_GRANT_READ_URI_PERMISSION`). Файл отдаётся
  во VLC через локальный HTTP-сервер телефона (`/file<ext>?id=…`)
  **с файлового дескриптора** (`FdFileSource` — без копирования
  файла), Range — перемотка работает. Если открыть fd не удалось —
  fallback: копия в `cacheDir/aircast-temp` (тоже автоудаляется).
- **Автоудаление — обязательно:** после каста (и при неудаче
  каста) — временная копия удаляется, fd закрывается
  (`cleanupCurrentFile`); stale-файлы чистятся при следующем
  запуске сервиса (`TempFiles.cleanup` в `onCreate`).
  Оригинал в галерее/Telegram не трогается.
- Длительность mp4 — из первых 128 КБ (`mvhd`), таймер конца
  работает. Resume для mp4-файлов нет (см. п. 4).

### 15. Instagram

  `og:video:secure_url` / `og:video:url` /

### 16. Twitch и Kick: master-first

- **Честно:** мастер Twitch (`usher.ttvnw.net/…m3u8`) не несёт

## v0.9.0 — авто-ретрай, авто-следующая серия, «поделиться логом», субтитры (2026-11-18)

Четыре фичи по решению Алексея (2026-11-18 03:34). Всё детерминированно,
без LLM в пути извлечения/воспроизведения. Не сделано (его же слово):
пульт в уведомлении, таймер сна, Piped, выбор качества вручную
(остаётся автовыбор лучшего).

### 1. Авто-ретрай: мёртвая ссылка больше не даёт вечную загрузку на ТВ

- Перед запуском каждого кандидата — **pre-flight проверка**
  (`StreamProbe.probeUrl`): Range GET первых байт (200/206 — жив),
  для HLS — GET master-плейлиста + первого варианта + Range GET
  первого сегмента. Редиректы — вручную, с Referer/Cookie на каждом
  шаге (как в прокси). Таймаут 2 с на запрос.
- Порядок попыток — тот же, что `pickBest` (`AutoCast.orderedAttempts`,
  максимум 3): master HLS — отдельным пулом, дальше по счёту
  формат×качество, без дублей.
- Если Companion сообщает об ошибке воспроизведения вскоре после
  запуска — тоже ретрай следующим кандидатом (а не сразу ошибка).
- Все попытки исчерпаны — честное «Видео недоступно — ни один
  источник не играет», а не тишина.

### 2. Авто-следующая серия: когда серия закончилась, следующая запускается сама

- **Как узнаём конец серии (исследование, честно).** Companion не
  сообщает состояние воспроизведения вообще: `MediaControlCommand` —
  это только команды Play/Pause/Next/Prev/Volume/Skip, а события
  `_iMC` несут только флаги управления (громкость и т.п.), не
  позицию. Настоящее состояние есть только в MRP (TCP 49152 +
  hand-rolled protobuf, `PlayerState.playback_state`, elapsed/duration)
  — отдельный протокол, кода в приложении нет. MRP — будущая работа,
  не v0.9.0.
- **Запасной метод — таймер по длительности.** Длительность берётся
  из: YouTube InnerTube `lengthSeconds`; HLS — сумма `#EXTINF`
  (через вариант-плейлист, если мастер); mp4 — `mvhd` из первых
  128 КБ (Range); DASH — `mediaPresentationDuration`.
  Таймер: длительность + 20 с на старт/буфер VLC.
- **Эвристика, а не точный конец:** пауза/перемотка с пульта ТВ таймер
  собьёт (следующая серия запустится раньше/позже). Если длительность
  не узнать — авто-следующая просто не вооружается, без таймера наугад.
- **Список серий** (`EpisodeList.parse`, generic, без сайтов):
  (1) ссылка-якорь «Следующая серия / Next», (2) группа ссылок,
  отличающихся от текущей страницы только номером эпизода
  (`/show/5,6,7`, `?ep=5,6`, `s01e05/e06`). Фильмы без списка серий
  не трогаются: списка нет — серия не вооружается.
- Следующая серия идёт тем же флоу (фоновая загрузка страницы серии
  → детект → запуск). Пока серия идёт — уведомление «Серия идёт —
  следующая запустится сама» с кнопкой «Отменить»; сервис живёт до
  конца серии и не останавливается сам. Новый share отменяет таймер.

### 3. Кнопка «Поделиться логом» в уведомлении «Видео не найдено»

- В уведомление о таймауте добавлено действие «Поделиться логом»:
  прозрачная `LogShareActivity` открывает системный share sheet
  с файлом `aircast.log` (свой `LogFileProvider`, без AndroidX —
  в проекте нет Gradle; отдаёт только `filesDir/aircast.log`, read-only).
- Когда видео НЕ найдено, движок пишет в лог диагностику (`diag`):
  URL страницы, title, последний JS-скан одной строкой
  (счётчики videos/urls/rel/jwfeeds/iframes/links/subs + src iframe),
  число кандидатов. Лог полезен для разбора без лишнего мусора.

### 4. Субтитры: два пути, оба — страховка друг друга

- Детект дорожек: `<track kind=subtitles/captions>` + `.vtt/.srt/.ass`
  в скриптах страницы (SCAN_JS, включая same-origin iframe).
- **Путь А — HLS-мастер с SUBTITLES-группой (основной для HLS).**
  Локальный прокси отдаёт синтетический мастер (`/subs-master`):
  исходный поток — единственный вариант, дорожки — группа
  `#EXT-X-MEDIA:TYPE=SUBTITLES` (язык + название). Все дорожки,
  выбор языка — во VLC. SRT → WebVTT и ASS → WebVTT (базово, стили
  теряются) конвертируются в приложении на лету (`/stream`); VTT —
  как есть.
- **Путь Б — параметр `sub=` в vlc-x-callback-url** (`CompanionClient.vlcDeepLink`,
  `vlc-x-callback://x-callback-url/stream?url=…&sub=…`).
  Подтверждён changelog VLC iOS 3.6.6 («URL decode the subtitles
  parameter for x-callback-url») и сторонними интеграциями (те же
  `&sub=<encoded>` для VLC и Infuse); на tvOS есть и фикс 3.3.8
  «Fix x-callback-url issue displaying the wrong subtitles».
  В `sub=` уходит первая дорожка через прокси (`/stream.vtt?u=…`,
  с расширением `.vtt`, Referer + конвертация). Для mp4 это
  **единственный** путь субтитров — HLS-мастер к mp4 неприменим.
- Оба пути идут одновременно: если один не сработает на tvOS,
  сработает другой. Худший случай — та же дорожка дважды в списке
  субтитров VLC (не мешает воспроизведению).
- **Честные ограничения (требуют живого теста Алексея):**
  отображение дорожек из HLS-мастера во VLC на tvOS — не проверено
  вживую; параметр `sub=` на tvOS — не проверен вживую
  (подтверждён только документацией/changelog и сторонним кодом);
  ASS — базовая конвертация (стили/позиции теряются); дорожки
  определяются только если они есть в странице/JS/трафике.

### Что НЕ проверено живым тестом (только Алексеем на ТВ)

## v0.5.2 — WebView на шаге 2 был 0 px + удаление прямого каста (2026-11-18)

Скриншот Алексея 2026-11-18 00:39: на шаге 2 между строкой URL и кнопкой
«НАЙТИ ВИДЕО» нет ни браузера, ни заглушки «Браузер загружается…» —
область нулевой высоты. При этом WebView работал: onPageFinished
срабатывал, JS-скан находил Kodik iframe, открывалась страница плеера.
Пользователь жал «ПЕРЕЙТИ» три раза, потому что на экране ничего не
происходило. Вероятно, браузер был невидим с самого появления мастера:
видео выбиралось из списка кандидатов (перехват сети/JS-скан), которым
видимость не нужна.

Причина — раскладка: экраны шагов добавлялись в корень без параметров
(WRAP_CONTENT по высоте), а контейнер WebView внутри шага 2 —
height=0 + weight=1. В LinearLayout с WRAP_CONTENT-высотой
weight-ребёнок получает 0 px: высота родителя равна сумме детей,
weighted-ребёнок при измерении равен 0, остатка для распределения нет.

Фикс (`LayoutContract.kt` — чистый Kotlin без импортов Android,
проверяется JVM-тестом):
- все 5 экранов шагов добавляются в корень с
  `LayoutParams(MATCH_PARENT, MATCH_PARENT)` — у видимого экрана
  фиксированная высота (остаток корня), вес внутри него распределяет
  реальное место;
- WebView добавляется в контейнер с явными
  `LayoutParams(MATCH_PARENT, MATCH_PARENT)`;
- у контейнера `minimumHeight = 200dp` как страховка от повторного
  схлопывания. Именно 200dp, а не 400dp: при dpi 560 400dp = 1400px, а
  фиксированный контент шага 2 ≈ 1520px — сумма превысила бы доступные
  ≈2550px и срезала бы низ экрана со списком кандидатов.
- Попутно чинится латентный баг остальных экранов: их корень —
  ScrollView, который при WRAP_CONTENT вырастал на всю высоту контента
  и срезал низ (скроллить было нечего — высота равнялась контенту);
  при MATCH_PARENT ScrollView получает остаток окна и скроллит.

  quad + полные UV), покрыта юнит-тестами.
- **Ключевая неопределённость — матрица SurfaceTexture (texMatrix).**
  Она НИГДЕ НЕ ЛОГИРОВАЛАСЬ: шейдер применяет её к UV кропа, и если
  там не только Y-flip, а поворот/масштаб/сдвиг (буфер повёрнут
  относительно контента), кроп по размерам буфера режет не ту ось —
  отсюда зум и сдвиг. При этом UV-дефект не может дать чёрные полосы
  при полном quad (CLAMP_TO_EDGE), а у f_2 они есть (121 слева, 145
  справа) — часть эффекта может быть контентом самих приложений
  (леттербокс видоискателя) или quad/viewport. Не гадать — сначала
  измерить (диагностика ниже), потом чинить.

### Исправление

- **Диагностика геометрии (первым делом).** На первом кадре сессии
  и при каждом изменении texMatrix в лог идут две строки:
  `GLES texMatrix: kind=... lin=[a=.. b=.. c=.. d=..] trans=(..,
  ..) m=[16 float]` и `GLES геометрия: buffer=.. (запрошен)
  content=.. режим=.. verts=[..] uv(buffer)=[..]`. Вид матрицы —
  `classifyTexMatrix` (IDENTITY / FLIP_ONLY / ROT_90 / ROT_180 /
  SCALE_TRANSLATE / GENERAL). Фактический размер буфера публичный API
  SurfaceTexture не отдаёт — логируется запрошенный
  (setDefaultBufferSize); кроп буфера виден по масштабу в матрице.
- **Кроп в пространстве буфера.** `mirrorRenderGeometry`
  (`MirrorGles.kt`): контентные размеры — из матрицы
  (`contentDimsFromMatrix`: при повороте 90° внутри буфера это
  перевёрнутые srcW/srcH), кроп — `mirrorCropGeometry` по
  контентным размерам, затем прямоугольник отображается в буфер:
  `finalUV = texMatrix * cropUV`, а в шейдер подаётся единичная
  `uTexMatrix`. Направление — прямое произведение, а не обратное:
  по доке `SurfaceTexture.getTransformMatrix` матрица отображает
  координаты изображения «to the texture coordinate that should be
  used to sample that location» (изображение → буфер); стандартное
  использование во всех сэмплах — `vTexCoord = M * aTexCoord`.
  Формула `inverse(M) * cropUV` была бы верна при обратной
  конвенции (M: буфер → изображение), которая противоречит доке;
  если живой лог покажет поворот и картинка останется не по той
  оси — направление меняется одной строкой в `mirrorRenderGeometry`.
  При flip-only — безопасный no-op: кроп-прямоугольники симметричны
  по v, finalUV-прямоугольник равен кропу (тест
  `texmatrix-flip-noop-rect`).
- **Поворот посреди сессии.** `MirrorCapture` слушает
  `DisplayManager.DisplayListener` (отдельный поток
  `MirrorRotation`); при смене размеров экрана — пересоздание
  VirtualDisplay + рендерера с новыми srcW/srcH, НЕ разрывая
  AirPlay-сессию: кодер (1920x1080), его drain-поток и MirrorClient
  не трогаются, heartbeat/TimeAnnounce идут, ТВ не видит разрыва.
  Поверхность кодера переживает rebuild (`releaseBlocking`:
  teardown + join потока рендерера; `release()` с флагом не
  отпускает encoderSurface при rebuild). Ворота rebuild —
  `mirrorRotationChanged` (только при реальной смене размеров).
  Регрессионный кейс — f_3: после поворота полоса обязана стать
  полноэкранной, а не леттербоксом.
- **Тесты.** 29 новых юнит-тестов: классификация матриц (identity /
  flip / rot90 / rot180 / масштаб+сдвиг / general / короткая),
  контентные размеры, flip no-op (прямоугольники для всех режимов
  и ориентаций + точные значения вершин FILL-портрета), rot90 FILL
  (точные значения + полоса буфера u ∈ [0.3721, 0.6279]), rot90
  STRETCH (полное покрытие), масштаб+сдвиг FILL, round-trip
  (обратная матрица от итоговых UV возвращает исходный кроп —
  для всех матриц × режимов × ориентаций), ворота поворота.
  Mock: `mock-v049-texmatrix-flip/rot90`,
  `mock-v049-geometry-flip-noop/rot90-fill` + verts/UVs в логе

## v0.4.8-mirror-avcc — Annex-B → AVCC: ДОКАЗАННАЯ причина чёрного экрана (2026-11-10)

Живой тест v0.4.7 (2026-11-10 14:59:25–15:00:15, 43 с): 391 кадр
закодировано / 390 отправлено, 11 IDR, 1 codec-кадр, heartbeat 43,
TimeAnnounce 44 — **ТВ по-прежнему чёрный**. Но в этот раз дамп
доказал причину, а не оставил очередную гипотезу. Независимый
верификатор (`tests/verify_mirror_dump.py`, построен только по
doubletake) против живого дампа: `decrypt_ok=390 decrypt_fail=0
avcc_ok=0 avcc_fail=390`, VERDICT: FAIL. Расшифровка работает (ключ,
nonce, AAD верны), codec-кадр валиден, timelineID верный — а **каждый
расшифрованный видео-кадр начинается с `00 00 00 01`** — Annex-B,
а не AVCC. Кадр #1 (IDR, 44483 B): `00 00 00 01 65 b8 42 7f ...`;
кадр #2 (P, 1096 B): `00 00 00 01 41 e4 04 7f ...`; каждый кадр —
ровно один NAL. ТВ ждёт AVCC (4-байтовая BE-длина перед каждым NAL)
и читает `00 00 00 01` как длину=1, следующая «длина» с offset 5 —
мусор («bad AVCC length 3091365887 at 5» и так все 390 кадров).
Декодер ТВ отвергал КАЖДЫЙ кадр — вот чёрный экран.

Корень: кодер MediaCodec (Qualcomm) на телефоне отдаёт кадры в
Annex-B, а наш путь отправки слал буфер кодера как есть, предполагая
AVCC — как у doubletake, где VideoToolbox отдаёт голые NAL'ы, и
каждый оборачивается в длину (`mirror.go:1790 avccWrap`, `:1550`
/`:1563`, `:2062` — «payload must be AVCC-encoded (4-byte BE length
per NALU, no start codes)»). Конвертации в doubletake нет, потому
что его источнику она не нужна; нашему — нужна. `parseNals` умел
НАХОДИТЬ NAL'ы в Annex-B (лог «NALs=1 первый тип=5»), но никто их
не конвертировал — это и был баг.

### Исправление

- **Конвертер** `annexBToAvcc` / `isAvcc` (`MirrorCapture.kt`,
  рядом с `parseNals`): каждый NAL — старт-код (4- или 3-байтовый)
  заменяется на 4-байтовую BE-длину; разбор — через существующий
  `parseNals`, второго парсера нет. Буфер, уже являющийся AVCC,
  возвращается как есть (последовательные BE-длины съедают буфер
  ровно); пустой и непарсящийся буфер — тоже как есть, конвертер
  не роняет сессию. Применяется в `sendFrameLocked` — единой точке
  отправки (и кадры из `onVideoFrame`, и придержанный первый IDR
  из `flushPendingKeyframe`), ДО шифрования и заголовка.
  Счётчик `framesConvertedAnnexB` — в итоге сессии; первая
  конвертация — в лог с размерами до/после.
- **Пин-вектор живого кадра #1** в юнит-тестах: `00 00 00 01 65 b8
  42 7f...` (44483 B) → AVCC `00 00 ad bf 65 b8 42 7f...`
  (44479 = 0xADBF), размер тот же. Всего 8 новых юнит-тестов:
  один NAL 4-байтовый / 3-байтовый старт-код, несколько NAL,
  уже-AVCC без изменений, пустой буфер, пин-вектор, негативный
  контроль (`isAvcc` на сыром Annex-B — false), обрезанный AVCC.
- **Мок исправлен — главный урок.** 238 mock-тестов кормили
  клиента готовыми синтетическими AVCC-кадрами, поэтому баг прожил
  7 сборок: `avcc_ok` на стороне mock-ТВ был зелёным при сломанном
  живом потоке. Теперь mock (`tests/MockTest.kt`, `annexBFrame`)
  подаёт кадры в формате РЕАЛЬНОГО кодера — Annex-B (IDR —
  4-байтовый старт-код, P — 3-байтовый), и клиент обязан
  конвертировать: проверка `mock-v048-annexb-to-avcc`
  (`framesConvertedAnnexB == 30`) + `mock-mirror-avcc` на стороне
  mock-ТВ + верификатор против дампа клиента из mock-прогона.
- **Негативный контроль** в `run_mock_test.sh`: срезанный живой
  дамп v0.4.7 (`tests/fixtures/live_v047_annexb_dump.bin` — все
  SETUP, codec-кадр, первые 3 видео-кадра; ключ — одноразовый
  сессионный, бесполезен после TEARDOWN) обязан ПРОВАЛИТЬ
  верификатор (`decrypt_ok=3, avcc_ok=0, avcc_fail=3`). Если он

  регрессия выше — фикция.

## v0.4.7-mirror-prove — TimeAnnounce: единственное, чего мы никогда не слали (2026-11-10)

Живой факт 2026-11-10 13:57–13:58 (v0.4.6): сессия ~34 с, 315 кадров
закодировано / 306 отправлено, 8 IDR, codec-кадр **правильный** (SPS
18 B profile 66 level 40 1920x1080, PPS 4 B, всего 37 B), PTS age
16–30 мс, skipRecord=true соблюдён (RECORD пропущен), аудио SETUP
вернул **реальные порты** (dataPort=54495, controlPort=55821),
feedback — все `{streams:[]}` (пусто), data-канал — тишина — **ТВ
по-прежнему чёрный**. Исправление Annex-B было реальным, но картину
не дало. Честно: после шести зеркальных сборок без картинки эта —
про доказательство, а не про очередную догадку.

### Вердикты по пяти подозреваемым (всё сверено с doubletake с нуля)

1. **Тело ответа video SETUP — НЕ ЧИТАЛОСЬ, ТЕПЕРЬ ЧИТАЕТСЯ.**
   Видео SETUP возвращал HTTP 200, 85 B, а мы логировали только имя
   ключа и dataPort. Теперь — **всё тело целиком** (как feedback с
   v0.4.6), плюс явный вердикт по `streamConnectionID` в ответе:
   совпадает / не содержит / ОТЛИЧАЕТСЯ. Важно: в заголовках кадров
   id **нет вообще** (ТВ привязывает поток по TCP-соединению к
   dataPort), так что чужой id в ответе кадры ронить не может —
   doubletake его вообще не читает. Ключ ChaCha всегда считается от
   **запрошенного** id. Mock-тест 15 (mock 7012,
   `--mirror-video-echo-id`): ответ несёт id+1000000, клиент логирует
   «ВНИМАНИЕ», ключ не меняет, кадры расшифровываются (decrypt_ok 1).
2. **Ключ шифрования видео — СОВПАДАЕТ С DOUBLETAKE БАЙТ В БАЙТ.**
   Перепроверено с нуля: doubletake `mirror.go:2203-2213`
   `deriveChaChaKey` — HKDF-SHA512, соль `"DataStream-Salt<id>"`
   (десятичный id), info `"DataStream-Output-Encryption-Key"`, IKM —
   pair-verify X25519 shared secret (fallback — сырой fpAesKey);
   nonce `[0,0,0,0]+LE64(counter)` с 0; AAD — полный 128-байтовый
   заголовок. Наш `deriveChaChaKey` (`fairplay/MirrorCipher.kt:157`)
   и `sendFrameLocked` — то же самое. Mock **независим**: примитивы —
   Python `cryptography` HKDF-SHA512 + ChaCha20-Poly1305 и свой X25519,
   а соль/info/nonce — из кода doubletake, проверены в исходнике;
   «общая неверная конвенция» означала бы баг в самом doubletake.
   Регрессия: pinned-вектор, посчитанный в Python (stdlib) по формуле
   doubletake (IKM 00..1f, id 1234567890123456789 →
   `c93b36fced0702083f662b78fa397ee834eebf04e8525e94c6876a10aec7525a`),
   плюс два негативных контроля (соль без id — другой ключ; FairPlay
   shk — не ключ видео-потока).
3. **Пустой feedback `{streams:[]}` — НЕ ПРИЧИНА, А СИМПТОМ.**
   Doubletake `feedbackLoop` (`mirror.go:2253-2290`) шлёт POST
   /feedback с **пустым телом** каждые 2 с и только логирует ответ —
   `streams` он не разбирает вообще. Наш код — тот же. «Streams» в
   ответе — про **аудио**-потоки (UxPlay возвращает type 96); Apple TV
   возвращает `[]` — «нет активных аудио-потоков». Это не сломанный
   запрос feedback, а следствие того, что мы не шлём аудио вообще.
   См. пункт про TimeAnnounce ниже.
4. **Heartbeat — ФОРМАТ ВЕРЕН, НО НИКТО ЕГО НЕ ВИДЕЛ.**
   Формат совпадает с doubletake (`mirror.go:2218-2251`: 128 B,
   [4]=0x02, [6]=0x1e, раз в 1 с после первого кадра), но в живом логе
   не было ни одной строки heartbeat. Теперь — счётчик
   `heartbeatsSent` в диагностике раз в секунду и в итоге сессии +
   строка первого heartbeat.
5. **Путь записи кадра — ТОЧЕН.** Два `write` + `flush` на Java
   Socket OutputStream пишут полностью или бросают (коротких записей
   в Java нет); doubletake пишет `net.Buffers` одним writev, а TCP —
   байтовый поток, разбиение не имеет значения. Теперь — одна строка
   при старте стрима: первый пакет, «построено N B, записано столько же».

### Главное новое: TimeAnnounce (RTCP sync) на аудио-control

Единственное, что реальный iPhone делает всегда, а мы — никогда:
**TimeAnnounce** — 28-байтовый UDP-пакет на аудио-control порт ТВ
(doubletake `audio.go:1179-1241 sendSyncPacketAt`, PTP-ветка):
`[0]=0x90` первый / `0x80` дальше, `[1]=0xd7`, seq 4, playheadRTP
дважды, `ptpNanoseconds(networkTime)`, timelineID. Первый — после
первого видео-кадра, потом раз в секунду. RTP-эпоха случайная 32-бит,
playhead = rtpNow − 7497 сэмплов (170 мс), networkTime — текущая метка
того же mediaClock, что у видео-кадров.

Почему это кандидат №1: ТВ в v0.4.6 **выделил реальные аудио-порты**
и ждёт аудио, а мы по аудио-транспортам не послали НИЧЕГО — ни RTP,
ни TimeAnnounce, ни RTCP. Doubletake в NoAudio-режиме тоже ничего не
шлёт — но NoAudio проверен только против UxPlay, а не против
настоящего Apple TV. Если рендерер ТВ ждёт аудио-часы (отображение
RTP↔сетевое время), прежде чем показать видео, без TimeAnnounce экран
чёрный навсегда, сколько бы кадров ни шло. Пакет — best-effort
(ошибка отправки сессию не роняет), счётчик — в диагностике и итоге.
Плюс читатель RTCP на том же сокете (первые 3 пакета — в лог с hex):
раньше этот сокет никто не читал.

### Два бага, пойманных mock-тестом (а не живым ТВ)

- **Дамп не создавался.** `MirrorStreamDump` создавал
  `FileOutputStream` инициализатором свойства — инициализаторы
  выполняются ДО `init`-блока, и `mkdirs()` в `init` не успевал:
  `FileNotFoundException (No such file or directory)`, если папки
  ещё нет. Исправлено: поток создаётся в `init`, после `mkdirs()`.
- **TimeAnnounce не уходил (EPERM).** Неподключённая UDP-отправка
  (`sendto` с адресом на каждый пакет) на песочнице-VM падает с
  `SocketException: Operation not permitted`, а подключённая —
  работает (проверено минимальным Java-тестом: unconnected FAIL,
  connected OK, пакет дошёл). Исправлено: сокет аудио-control
  `connect()`ится к ТВ один раз до запуска потока, пакеты шлются
  без адреса — это ровно то, что делает doubletake (dialed UDP conn)
  и наш PTP-канал; на реальном телефоне неподключённая отправка
  тоже работает, так что поведение на ТВ не меняется, а mock-тест
  теперь проверяет анонсы по-настоящему (29 пакетов за сессию,
  `announce_ok: true`).
- **Урок харнесса:** верификатор дампа клиента обязан брать ключ
  ПЕРВОЙ mirror-сессии (`shared_secrets[0]` +
  `video_setup[0].streamConnectionID`), а не последние значения из
  summary — иначе все кадры «не расшифруются», хотя шифр верен
  (mock сам расшифровал 210/210). Mock теперь пишет
  `shared_secrets` списком, а `run_mock_test.sh` гоняет верификатор

Эта сборка — четыре вещи, которые ТВ мог нам говорить, а мы никогда
не читали, плюс исправление найденного бага.

### 1. SPS со старт-кодом Annex-B — НАЙДЕННЫЙ БАГ, ИСПРАВЛЕН

Кодер Qualcomm отдаёт csd-0/csd-1 **с префиксом** `00000001` (SPS
22 B вместо 18, PPS 8 B вместо 4). Наш `decodeSps` проверял
`sps[0] & 0x1F != 7` → `0x00` → null («SPS не разобрался»). Хуже:
`buildAvccConfig` писал `sps[1..3]` как profile/compat/level →
`0x00, 0x00, 0x01` — codec-кадр уходил с **avcC profile=0/level=1 и
SPS с префиксом** (45 B — ровно как в живом логе). Такой codec-кадр
невалиден по ISO 14496-15, и декодер ТВ его, скорее всего, отвергает
— это главный подозреваемый чёрного экрана с v0.4.0. Mock ловил
такой кадр («codec frame: bad SPS»), но тесты кормили его
синтетическим чистым SPS — реальный путь не упражнялся. Исправлено:
`stripAnnexBStartCode` + снятие префикса в `decodeSps` и на границе
`onCodecConfig` (теперь `latestSPS`/`latestPPS` всегда чистые).
Тесты: живой вектор `67428028da01e0089f966a0a0c0a0da1426a` →
profile 66 / level 40 / 1920x1080 / crop bottom 4 / VUI present
(и префиксная форма — тот же результат); avcC из чистого SPS —
profile 66/0x80/40, длина SPS 18; mock-секция 14(c) — префиксный
SPS через реальный `onCodecConfig` против mock 7010: avcc_ok +2
(1 codec + 1 IDR), avcc_fail 0, без «bad SPS», sps_len 18, в логе
`profile=66`.

### 2. Тело ответа /feedback — ТЕПЕРЬ ЧИТАЕМ

Каждый feedback возвращал HTTP 200 с ключом `streams`, а мы писали
в лог только имя ключа. Теперь — **всё тело целиком** одной компактной
строкой раз в 2 с (`formatPlistCompact`; тело маленькое, ~55 B).
Doubletake логирует так же (`[FEEDBACK] response: %+v`) и его
receiver возвращает `{"streams": [{"type": 96, "sr": 44100}]}` —
mock теперь возвращает именно это тело, и тест проверяет, что в
логе есть строка `Feedback:` с `44100`. Если ТВ сообщает об ошибке
потока или состоянии «waiting» — следующий живой лог это покажет.

### 3. skipRecord из control SETUP — ТЕПЕРЬ ЧИТАЕМ И СОБЛЮДАЕМ

Doubletake читает `skipRecord` из **control SETUP** (mirror.go:888),
а из аудио-ответа — только в media-first порядке (line 987); RECORD
пропускается, если true (line 1110). Мы читали его только из аудио-
ответа, где ключа нет (только `streams`) → всегда false → RECORD
слался всегда. А в живом логе v0.4.5 ключ в ответе control SETUP
**есть** («ключи: skipRecord,info,eventPort,…»), значение никто не
читал. Исправлено: в control-first порядке — из control-ответа, в
media-first — из аудио-ответа; значение логируется с пометкой
«нет ключа», если ключа нет; `skipRecord` — поле клиента. Mock:
второй экземпляр 7011 (`--mirror --skip-record`, control SETUP
говорит `skipRecord: true`, аудио — `false`); тест 14(d): setup OK,
state streaming, `skipRecord=true`, mock `record == 0`, в логе
`RECORD пропущен (skipRecord)`, кадры при этом идут (5/5).

### 4. Входящие data-канала — ТЕПЕРЬ ЛОГИРУЕМ

Монитор data-канала читал входящие и молчал (кроме редкого
«неожиданные N B»). Теперь — hex первых 64 B + длина каждого чанка
(`hexHead`), счётчики `dataInboundChunks`/`dataInboundBytes` и итог
сессии в finally («тишина», если ничего не пришло). Mock шлёт
тестовую пробу `deadbeef` при подключении data-канала (только mock —
живой ТВ ничего не шлёт); тест проверяет строку `Data-канал:`
с `deadbeef` в логе.

### 5. Audio SETUP dataPort=0 — ВЕРДИКТ: НЕ БЛОКЕР ВИДЕО

С v0.4.3 аудио SETUP (dict form) возвращает dataPort=0, а legacy
fallback v0.4.2 — реальный порт (55653). Разобрано по doubletake
(`plistStreamPorts`, mirror.go:2386): порты берутся с верхнего уровня
ответа + из `streamConnections` (RTP→dataPort, RTCP→controlPort,
если > 0); если `audioDataPort==0` — doubletake пишет «receiver did
not provide audio ports, skipping audio» и **продолжает с видео**.
Наш аудио-дескриптор сверен с doubletake поле в поле и не менялся.
Добавлено только чтение портов способом doubletake + их лог в
«Audio SETUP OK» (на случай, если ТВ отдаёт порты внутри
`streamConnections`, а наш прежний top-level-only парсер их не видел)
и лог наличия `streamConnections` в ответе. Аудио мы всё равно не
шлём (видео-only), и мёртвый аудио-поток видео не блокирует.

Остальное без изменений: PTS из `elapsedRealtimeNanos`, soTimeout=0,
аудио dict form, вложенный разбор /info, придержанный первый IDR,
сторож ключевых кадров, pacing 30 fps, размер codec-кадра из SPS,
ts/tid/якорь в логе, состав NAL в строках IDR. Низкая/переменная
частота кадров (0–28 fps на статичном экране) — норма, не гонимся.

### Подозреваемый 1 — метки кадров в таймлайне ТВ (PTP): ОПРОВЕРГНУТ как баг, добавлена диагностика

Строка лога «timeline=0x48e15c43a0270008» одинакова во всех живых
прогонах (07:34, 08:12, 08:58) — это НЕ показание часов, а **ClockID:
идентификатор PTP-часов ТВ** (doubletake `mediaClock.timelineID =
plistUint64(timingPeerInfo["ClockID"])`). Идентификатор обязан быть
постоянным — его одинаковость across runs это норма, а не дефект.
Якорь сверен построчно с doubletake: `receiverClockTimestamp`
(received+processing → compact), `at()` (якорь + compact(delta +
bias)), `reanchor` (никогда назад), `updateTimingPeerInfo`,
формула compact timestamp, bias 100 мс (high-профиль для Wi-Fi,
`screenLatenciesForHint`) — всё совпадает. Mock независимо проверяет
ts ≥ якоря, монотонность и tid == ClockID. Исправлять тут нечего —
но «возраст PTS 20 мс» измеряется в НАШИХ часах и ничего не говорит
о том, что получает ТВ. Добавлено: первый кадр и дальше раз в 10 с
в лог пишутся сырые `ts`/`tid`/якорь в hex («Кадр: ts=0x…
tid=0x… якорь=0x…»), а `lastFrameTs`/`lastFrameTid`/`anchorTs`
выставлены наружу для тестов. Следующий живой лог покажет, в
прошлом кадры, в будущем или вовремя — в домене ТВ, а не нашем.

### Подозреваемый 2 — SPS / параметры кодека: НЕИЗВЕСТЕН (байтов не было), добавлены разбор и лог

Кодер: Baseline, Level 4, 1920x1080, SPS 22 B + PPS 8 B — легально
(Level 4.0: макс. 245760 МБ/с, 1080p30 = 244800 МБ/с; 8 Мбит/с
далеко ниже лимита). Но байты SPS в живом логе никогда не
появлялись — декодировать их было не из чего. Добавлено: порт
doubletake `spsDimensions` + `h264BitReader` + `stripEmulationPrevention`
(`decodeSps`, JVM-тесты на фикстуре 1920x1080 High/31 и реальном
Baseline SPS от libx264: 1920x1080, level 40, VUI). `onCodecConfig`
теперь пишет в лог SPS/PPS hex + profile/level/размеры/VUI и
предупреждает, если размер из SPS ≠ холсту. И одно реальное
изменение по doubletake: размер растра в codec-кадре теперь берётся
из SPS (`codecHeaderDimensions`), а не из холста — doubletake делает
именно так в `flushVCL` перед `sendCodecFrame`. Вопрос «codec-кадр
перед каждым IDR или один раз» закрыт: doubletake шлёт его только
при смене конфига («Repeating an identical configuration before
every IDR is unnecessary and some receivers treat it as
reconfiguration») — фикс v0.4.4 верен.

### Подозреваемый 3 — 128-байтовый заголовок + шифр: ОПРОВЕРГНУТ

Перепроверено свежим взглядом по `mirror.go`: LE длина, тип/флаги,

## v0.4.4-mirror-keyframe — ТВ чёрный 52 с при живых кадрах: ключевые кадры (2026-11-10)

Живой факт 2026-11-10 08:12–08:13 (v0.4.3): keepalive сработал —
сессия жива ~52 с, feedback 200, холст 1920x1080 (displays=1), audio
SETUP с первой (dict) формы, возраст PTS 13–47 мс (фикс часов
работает), 2203 кадра закодировано / 2143 отправлено / 41,5 МБ —
пользователь остановил сам. **Но ТВ чёрный всё время** («Черный
экран», Алексей 08:13). Кадры текут со свежими PTS и верным шифром,
а ТВ ничего не показывает. Декодер ТВ не может начать показ без
ключевого кадра (IDR) — разбор лога и кода дал три дефекта и один
диагностический провал.

### Дефект 1 — первый IDR терялся до старта стрима (подтверждено арифметикой)

Захват стартует в `onCanvas` (шаг 6 setup), а `streaming=true` —
только на шаге 12 (после audio/video SETUP, data-канала и RECORD).
Между ними кодер уже выдаёт кадры, и первый из них — IDR. Старый
`onVideoFrame` выбрасывал кадры до `streaming=true` молча ранним
return, без счётчика. Лог: в первую секунду закодировано 69,
отправлено 9, пропущено 36 — 69−36−9 = **24 кадра ни отправлено, ни
«пропущено»**, и разрыв ровно 24 держится всю сессию. Это и есть
окно до streaming=true — первый IDR почти наверняка среди них.
Исправлено: IDR до стрима придерживается (`pendingKeyframe`) и
уходит первым при старте стрима (`flushPendingKeyframe`, метки
времени — «сейчас», как фикс PTS в v0.4.3); не-IDR до стрима
считаются отдельно (`droppedPreStreaming`).

### Дефект 2 — буфер CONFIG|KEY_FRAME выбрасывал IDR

Первый буфер ряда кодеров (в т.ч. Qualcomm) несёт одновременно
`BUFFER_FLAG_CODEC_CONFIG` и `BUFFER_FLAG_KEY_FRAME` (SPS+PPS+IDR
в одном). Старый `drainEncoder` считал такой буфер только конфигом
и молча выбрасывал IDR внутри него. Исправлено: IDR NAL'ы (тип 5)
достаются (`extractIdrAvcc`) и отдаются как ключевой кадр, SPS/PPS —
в `onCodecConfig` как раньше.

### Дефект 3 — нет сторожа ключевых кадров

Кодер настроен на IDR каждые 2 с (`KEY_I_FRAME_INTERVAL=2`), но
если он перестаёт их давать, пока кадры идут, ничто это не
замечает. Добавлен сторож: нет IDR 2 с после старта стрима (до
прайминга) или 4 с после последнего IDR (после прайминга) —
запрос sync-frame у кодера (`MediaCodec.setParameters`,
`KEY_REQUEST_SYNC_FRAME`), троттлинг 1 раз в 2 с. Решение —
чистая функция `needsSyncFrame` (JVM-тестируется).

### Диагностический провал — лог не отвечал, уходил ли хоть один IDR

Чекпоинты «IDR=false» на кадрах 300/600/…/2100 — это 7 одиночных
кадров из 2203: при GOP ~60 кадров все семь не-IDR с вероятностью
~89%, они ничего не доказывают. А счётчика IDR в диагностике не
было вообще. Теперь: каждый IDR — в счётчик `idrFramesSent` и в
лог («IDR отправлен: #N, … B, возраст PTS … мс»), каждый
codec-кадр — в лог с размерами SPS/PPS, каждый пропуск — с
причиной (первые 10 по одному, дальше каждая 50-я) и разбором в
диагностике (`до стрима/не IDR/без SPS/часы`), интервал ключевых
кадров — в стартовом логе кодера. Следующий живой лог ответит,
уходил ли IDR, прямо, а не догадками. Честно: код не доказывает,
что IDR не уходил вообще (кодер запрашивает IDR каждые 2 с, и
код их отправляет, когда они есть) — фикс гарантирует, что IDR
теперь точно уходит при старте и запрашивается при пропаже, а лог
покажет, что происходит на самом деле.

### Попутно — темп 30 fps

Рендерер рисовал на каждый `onFrameAvailable` (экран 120 Гц) —
всплески 60–119 fps и «Медленная запись кадра: 90/107 мс»

## v0.4.3-mirror-keepalive — ТВ ничего не показывал + сессия умирала через 5 с (2026-11-10)

Живой факт 2026-11-10 07:34–07:35 (v0.4.2): захват работает — три
попытки, 106/143/180 кадров закодировано, FairPlay SAP OK, control

каждая сессия умирала через ~5 с: «Поток остановлен: data-канал:
Read timed out». Два отдельных бага.

### Причина 1 — PTS кадра из другого домена часов (главная: чёрный экран)

`MirrorGles.drawFrame()` ставил в `eglPresentationTimeANDROID`
`SurfaceTexture.timestamp` — это CLOCK_MONOTONIC (останавливается
в suspend; Android docs: zero point «depends on the source»,
timestamp «cannot generally be compared» с другими часами). А
`MirrorClient.frameTimeAt()` сравнивает PTS с `bootNowMs()` —
`elapsedRealtime()`, CLOCK_BOOTTIME. Разница двух часов — всё
время suspend телефона с загрузки. Кадры уходили с метками в
прошлом, которые ТВ отбрасывает как опоздавшие (или наш же
age-check 30 с их молча пропускал). Исправлено: PTS ставится из
`SystemClock.elapsedRealtimeNanos()` в момент рендера (тот же
домен, что и `bootNowMs()`, по построению) + монотонная защита.
Комментарий в коде, утверждавший обратное («same domain as
elapsedRealtimeNanos»), был неверен. Весь остальной путь кадра
сверен с doubletake поле за полем и совпадает: заголовок 128 B,
avcC, ChaCha20-Poly1305 (HKDF-SHA512, nonce [0,0,0,0]+LE64,
AAD = заголовок), shk/shiv, дескрипторы SETUP, порядок RECORD,
heartbeat, priming codec-кадром перед первым IDR — mock
независимо расшифровывает кадры (decrypt_ok=30, avcc_ok=31).

### Причина 2 — таймаут чтения data-канала убивал сессию

Data-канал — наш uplink для кадров, ТВ ничего обратно не шлёт.
Но сокет создавался с `soTimeout = 5000`, а монитор `startDataMonitor()`
вызывал `failStream()` на ЛЮБОМ исключении чтения — `Read timed out`
через 5 с ронял сессию. У doubletake на dataConn дедлайна чтения
нет вообще (только SetWriteDeadline при записи). Исправлено:
`soTimeout = 0`, `SocketTimeoutException` = простой (редкий лог,
продолжаем); сессия завершается только на реальный EOF/закрытие
ТВ, ошибку записи, стоп пользователя, повторные падения feedback
или onStop проекции.

- Audio SETUP: первая форма слала `streamConnections` СПИСКОМ —

- Диагностика раз в секунду в логе: закодировано (fps),
  отправлено (fps), байт (КБ/с), пропущено, возраст PTS (мс),

## v0.4.0-mirror — зеркало экрана (2026-11-10)

### Почему зеркало, а не прямой каст

Прямой каст мёртв на этом ТВ (Apple TV 4K AppleTV14,1, tvOS 27.2):
`POST /play` всегда 200, но ТВ никогда не загружает видео; `POST
/command insertPlayQueueItem` всегда HTTP 400 во всех формах
(PR-точные минимальная #2846, полная #2899, +messageID, mp4 и HLS
Apple BipBop), при этом probe `playbackInfo` на том же соединении
возвращает 200 (с телом-ошибкой, код -6707 — плеера нет). PTP так и
не включился (Delay_Req 0). PigeonCast работает на этом же телефоне
и ТВ — только через зеркало экрана. Зеркало — и единственное место,
где работает управление соотношением сторон: кадр 20:9 кропается /
масштабируется до 16:9 **до кодирования**.

### Как работает зеркало (протокол, doubletake)

- **Сеанс**: `GET /info` → HAP Pair-Verify (сохранённые credentials;
  секрет X25519 — база ключей) → `POST /fp-setup` ×2 (FairPlay SAP,
  режим 3) → control SETUP → audio SETUP (type 96, заглушка без аудио)
  → video SETUP (type 110) → TCP data-канал → RECORD (если не
  skipRecord) → кадры + heartbeat 1 с + `POST /feedback` 2 с +
  event-канал. Стоп: TEARDOWN на audio URI.
- **FairPlay SAP** (NOT HAP — для ключей медиа): FPLY-записи m1/m2/m3/m4;
  SAP-сообщение — инверсные AES-раунды с middle-ключами по режимам
  (CBC, mode 3 — блоки 7→0); обмен — white-box (modified MD5 + SAP
  hash + descriptor/masks/networks); wrapping key — HMAC-SHA1 +
  AES-128-ECB; master key — SHA-512(fpAesKey || HAP-секрет)[:16]
  (HAP pair-verify всегда смешивает). Порт — `fairplay/` (Kotlin,
  LGPL-3.0), проверен 255 тестами по золотым векторам doubletake.
- **Тайминг**: PTP (ТВ заявляет feature 41, sourceVersion 980.71.1) —
  якорь из заголовков SETUP (`X-Apple-RequestReceivedTimestamp` +
  `X-Apple-ProcessingTime`) + ClockID; reanchor на каждом `/feedback`;
  `updateTimingPeerInfo` с event-канала. NTP — фолбэк (свой responder
  с boot-временем, не wall-clock).
- **Кадры**: TCP data-канал, заголовок 128 Б + payload. Codec-кадр
  (SPS+PPS, avcC, тип 0x01) — перед первым IDR и при смене SPS/PPS.
  Видео-кадр — AVCC (4-байтные длины NAL), тип 0x00, флаг 0x10 = IDR,
  метка времени — compact timestamp на таймлайне ТВ, timelineID =
  ClockID (PTP). Шифр — ChaCha20-Poly1305 (HKDF-SHA512 от HAP-секрета,
  salt `DataStream-Salt<streamConnectionID>`, nonce `[0,0,0,0] +
  LE64(счётчик)`, AAD = заголовок 128 Б); AES-CTR — фолбэк без HAP.
- **Захват (Android)**: MediaProjection (системный диалог) →
  VirtualDisplay → SurfaceTexture → GLES-рендерер (кроп) → MediaCodec
  H.264 (1920×1080, 30 fps, ~8 Мбит/с, I-кадр каждые 2 с) →
  MirrorClient. Foreground-сервис `MirrorService`
  (`foregroundServiceType="mediaProjection"`).
- **Кроп**: FILL (по умолчанию) — центральный кроп 20:9 → 16:9
  (1264×2780 → видимая полоса 1264×711 → 1920×1080, без полос);
  FIT — весь экран с полосами по бокам; STRETCH — растяжение.
  Поворот mid-session — ограничение v1: начинать зеркало в той
  ориентации, в которой будете смотреть.
- **Латентность**: Wi-Fi, профиль high — видео 100 мс, аудио 170 мс
  (7497 сэмплов @ 44.1 кГц). Аудио в v0.4.0 не передаётся (video-only);
  дескриптор audio — заглушка AAC-ELD/ALAC по маске `screenStream`.

## Почему это решает проблему чёрных полос

Телефон Алексея — realme GT 7 Pro, экран 1264×2780 (20:9). При касте
«экрана браузера» на ТВ 16:9 видео получает двойные полосы: полосы
браузера + полосы от экрана 20:9.

AirCast **не зеркалит экран телефона**. Он извлекает прямую ссылку на
видео (mp4 / HLS .m3u8) из страницы и отдаёт её Apple TV командой
`play_url` — ТВ сам скачивает и показывает видео. Видео 16:9 при этом
заполняет ТВ нативно, полос нет. В приложении честно показано
соотношение сторон найденного видео и пояснение, что прямой каст
кропа не имеет (см. «Честность про aspect ratio» ниже).

  первом спаривании (Pair-Setup, SRP-6a, 3072-бит, SHA-512);
  дальше переподключение без ПИН.

### Зеркало экрана (v0.4.x)

- `MirrorClient.kt`: GET /info → HAP Pair-Verify → /fp-setup ×2
  (FairPlay SAP, mode 3) → control SETUP → audio SETUP (type 96,
  заглушка — звука нет) → video SETUP (type 110) → TCP data-канал →
  кадры H.264 AVCC + heartbeat 1 с + POST /feedback 2 с + event
  channel; PTP media-clock anchor из control SETUP.
- Кадры: MediaProjection → VirtualDisplay → SurfaceTexture → GLES
  (кроп Fit/Fill/Stretch) → MediaCodec H.264 1920×1080, 30 fps,
  Annex-B → AVCC перед отправкой (v0.4.8: Annex-B был причиной
  чёрного экрана), ChaCha20-Poly1305 (ключ — HKDF-SHA512 от HAP
  secret, как в doubletake).
- Поворот телефона посреди сессии: v0.4.9 пытался пересоздать
  VirtualDisplay — платформа запрещает второй createVirtualDisplay
  на том же MediaProjection (SecurityException, живой вылет
  2026-11-10 16:14). Начинайте зеркало в той ориентации, в какой
  будете смотреть.

Весь код AirPlay — чистый Kotlin без зависимостей (нет androidx/Gradle
на этой ВМ): SRP-6a, X25519/Ed25519 (pure Kotlin, проверены векторами
RFC 7748/8032), ChaCha20-Poly1305 (платформенный cipher, API 28+),
HKDF (HmacSHA512, RFC 5869), binary plist (writer + reader),
HAP TLV8. Адаптировано из CenturyPlay (Kotlin,
AirPlay 2 audio) и pyatv (Python, протокол).

### Kodik: извлечение ссылки

YummyAnime не хостит видео сам — плеер Kodik в iframe. Приложение:

1. В WebView перехватывает сетевые запросы `.m3u8/.mp4/.mpd` (включая
   запросы из iframe Kodik) и JS-сканирует `<video>` + `<iframe>`.
2. Показывает панель «Найдено видео» с кандидатами (URL, качество,
   формат) — выбор вручную.
3. Выбранная ссылка запускается во VLC на ТВ (Companion _launchApp);
   VLC сам забирает видео по ссылке. Локального прокси больше нет
   (HlsProxy удалён в v0.5.2 вместе с прямым кастом).

### Aspect ratio — честно

AirPlay-каст **не имеет параметра кропа** на ТВ — слайдер кропа,
который ничего не делает, в приложении отсутствует намеренно.

- Приложение показывает обнаруженное соотношение сторон видео
  (например, 16:9, 21:9) и объясняет: 16:9-источник заполняет ТВ
  нативно, двойные полосы исчезают, потому что экран телефона
  не зеркалится.
- Режимы **Fit / Fill-Crop / Stretch** хранятся на каждый сайт и
  применяются к **встроенному превью-плееру** в приложении
  (TextureView + MediaPlayer) и к **зеркалу** (кадр 20:9
  кропается/масштабируется до 16:9 до кодирования — на ТВ без полос
  при «Заполнить экран», верх и низ экрана телефона обрезаются).

### Диагностика (экран «Диагностика»)

- Найденные по mDNS устройства (`_airplay._tcp`), модель, IP/порт.
- Дамп `/server-info` и расшифровка feature bits.
- Состояние спаривания (есть ли сохранённые credentials).
- Лог извлечения плеера, статус зеркала (кадры, IDR, heartbeat),

  в лог и на экран.

## v0.1.2 — доказанная причина вылета + фиксы по живому логу (2026-11-09)

v0.1.1 на телефоне Алексея **запустилась**. Её лог доказал причину
вылета v0.1.0 — больше не «неизвестно»:

1. **ПРИЧИНА ВЫЛЕТА v0.1.0 — ДОКАЗАНА.** Строка лога:
   `TextureView/PreviewPlayer init failed: TextureView doesn't support
   displaying a background drawable`. В v0.1.0 `buildBrowserScreen`
   создавал превью-`TextureView` с `setBackgroundColor(Color.BLACK)`.
   `TextureView` бросает `IllegalStateException` на любом
   `setBackground*` — в `onCreate`, ДО `setContentView`, отсюда
   мгновенный вылет без единого кадра UI. v0.1.1 выжила только за счёт
   `try/catch`, превью было отключено. **Исправлено в v0.1.2:**
   никакого `setBackground*` на самом `TextureView` — чёрный фон
   теперь на контейнере (`FrameLayout`) вокруг него. Превью снова
   работает (проверяется кнопкой «Превью» на тестовом видео).
   Проверка grep: в коде не осталось вызовов `setBackground*` на
   `TextureView` (остались только на `LinearLayout`/`TextView`/
   `FrameLayout` — им фон разрешён).
2. **JS-скан был сломан на каждом запуске.** Лог повторял `JS scan
   parse error: ... cannot be converted to JSONObject`. Причина:
   `WebView.evaluateJavascript` отдаёт результат JS как
   JSON-закодированную СТРОКУ (в кавычках, с экранированными
   кавычками внутри), а код делал `JSONObject(json)` напрямую.
   **Исправлено:** `VideoUrls.parseScanResult()` (чистый Kotlin, без
   `org.json` — тестируется на JVM) сначала разворачивает строку
   (`decodeJsResult`, включая `\uXXXX`), затем извлекает `videos[]`
   и `iframes[]`. Новый unit-тест: закодированная строка как от
   WebView → корректные видео и фреймы; `null`/пусто → пустой
   результат; кириллица в `\uXXXX` декодируется.
3. **Плеер на странице — Alloha, не только Kodik.** Страница серии
   отдаёт iframe плеера (Alloha) с параметрами фильма/перевода/
   сезона/серии. Старый `isKodik()` его не узнавал, `kodikIframeUrl`
   оставался `null` — отсюда «Открыть плеер: iframe не найден».
   **Исправлено:** общий детектор `VideoUrls.isPlayerIframe()`
   (Alloha, Kodik, `/player`, `/embed`, `embed.`/`player.`-хосты,
   `/serial/`) и `playerIframeUrl`; кнопка «Открыть плеер» открывает
   найденный плеер. Поддержка Kodik сохранена. В логах URL плеера
   печатается только как хост+путь без query (`safeHost`) — токены
   из query никуда не пишутся.
4. **`/server-info` 403 затирал features.** До спаривания ТВ отвечает
   на `GET /server-info` HTTP 403 с пустым телом, а код перезаписывал
   `features` на `0x0` («нет известных битов»), хотя mDNS уже дал
   правильные features (V1+V2). Плюс `selectDevice()` сам дёргал
   проверку — повторные тапы спамили ТВ (~10 запросов за секунды).
   **Исправлено:** (а) HTTP-код != 200 трактуется как «требуется
   сопряжение»: данные из mDNS (features/модель) сохраняются, ничего
   не перезаписывается нулём, в Диагностике пишется объяснение;
   (б) `selectDevice()` больше не вызывает проверку автоматически —
   только кнопка «Проверить /server-info» или один раз после
   успешного спаривания; (в) дебаунс 2 с + защита от параллельных
   запросов проверки.
5. **Мелочь:** плейсхолдер `blank.mp4` (plyr.io) больше не попадает
   в «Найдено видео» (`VideoUrls.isPlaceholder`). Путь перехвата
   сети НЕ трогали — он работает: именно он нашёл HLS master
   `.m3u8` плеера (в URL — 2160p).
6. **Сохранено из v0.1.1 без регрессий:** CrashHandler в Application,
   маркеры запуска, ленивый WebView, экран краша, безопасный режим,
   nullable preview/webView, иконка.

## v0.1.3 — два провала живого теста v0.1.2 и их исправления (2026-11-09)

Живой тест v0.1.2 на реальном телефоне + Apple TV (08:02–08:04)
провалился двумя независимыми способами. Оба исправлены здесь.

### Провал A — каст шёл на страницу плеера, а не на видео

Все 5 попыток каста целились в Kodik `storage.html` (HTML-страница
плеера в iframe) — приложение предлагало её как кандидата
(«JS: iframe плеер»), а превью MediaPlayer тоже падало на ней
(`what=1`). Настоящие видео-кандидаты при этом БЫЛИ найдены
перехватом сети (HLS master `.m3u8`, 2160p; варианты 360p/720p) —
и ни разу не кастанулись. Дополнительно эвристика `"/video/"`
в `isVideoUrl` пропустила `/api/video/291174` как «видео».

**Исправлено:**

- Кандидаты в «Найдено видео» — только настоящие видео-URL:
  `.m3u8/.mp4/.mpd/.mov/.m4v/.webm` в пути (без учёта регистра),
  включая форму `.../720.mp4:hls:manifest.m3u8`, плюс endpoint
  Google `videoplayback`. Эвристики `"/video/"` и подстроки `m3u8`
  в query — убраны (`VideoExtractor.kt`, строгий `isVideoUrl`).
- Страницы плеера (Kodik season, Alloha, `storage.html`, любой
  HTML-iframe) в кандидаты НЕ попадают вообще — они хранятся только
  как `playerIframeUrl` для кнопки «Открыть плеер».
- Перед кастом и перед превью URL валидируется: не-видео
  блокируется сообщением «Это страница плеера, а не видео. Выберите
  .m3u8/.mp4 из списка „Найдено видео“», на ТВ ничего не уходит.
- Лог прокси больше не врёт: `localUrlFor()` возвращает исходный
  URL как есть для не-`.m3u8/.mp4/.mov` — теперь в логе честно
  «каст напрямую (прокси не переписал URL)». Заодно из лога убран
  полный URL с токеном (только хост+путь и маршрут прокси).

### Провал B — pair-verify M4 error 2 (блокер)

Каждая попытка каста умирала здесь — 5 раз, включая сразу после
свежего успешного Pair-Setup (08:03:49, PIN введён, данные
сохранены):

```
POST /pair-verify -> HTTP 200 (159 B)   [M2]
POST /pair-verify -> HTTP 200 (6 B)     [M4, TLV error 2 = authentication]
playUrl exception: pair-verify M4 error 2
```

**Что найдено (сверка с pyatv и CenturyPlay, а не гадание):**

- Pair-Setup M1–M6 проходит — значит, SRP, HKDF, ChaCha20-Poly1305,
  Ed25519-подпись M5 работают против настоящего ТВ.
- В `verify()` M2 расшифровывается и подпись сервера проверяется —
  значит, общий X25519-секрет, сессионный ключ, ChaCha и nonce
  PV-Msg02 верны. Падает ТОЛЬКО проверка ТВ нашей подписи M3.
- Точное расхождение — **порядок байт в подписываемых данных M3:**
  - pyatv `auth/hap_srp.py` `verify1`: `device_info =
    self._public_bytes + credentials.client_id + session_pub_key`,
    т.е. **наш публичный ключ + наш id + публичный ключ сервера**;
  - CenturyPlay `HapPairing.kt` `verify()`: то же —
    `ourPublic + clientId + serverPublic`;
  - **наш код v0.1.2 подписывал `serverPublic + clientId + ourPublic`**
    (порядок как в M2). ТВ проверяет подпись по другому байтовому
    набору — и отвечает M4 error 2. Подписи при этом «валидны»
    криптографически, просто посчитаны не над теми данными.
- Почему mock-тест v0.1.2 это не поймал: `tests/mock_airplay.py`

### Как тестировать v0.1.3 (Алексей)

3. Каст: выбрать перехваченный `.m3u8` (2160p или 720p, прокси ВКЛ)

   `POST /play -> HTTP ...` и `/playback-info -> HTTP ...`.
4. Если снова `pair-verify M4 error 2` — нажать «Спарить заново»

   (`pair-verify M1/M2/M3/M4` — там теперь длины и сырые байты TLV

## Известные ограничения (честно)

1. **Прямой каст мёртв на tvOS 27.2 (решено 2026-11-10) и удалён
   в v0.5.2 (2026-11-18).** `/play` 200 + чёрный экран +
   `/playback-info` 500; `POST /command insertPlayQueueItem` —
   HTTP 400 во всех формах (шесть сборок v0.3.0–v0.3.5, PR-точные
   тела, mp4 и HLS BipBop), при этом probe `playbackInfo`
   возвращает 200 с телом-ошибкой (-6707, плеера нет). ТВ отказывает
   сторонним отправителям в постановке видео в очередь. Рабочий
   путь — **только VLC через Companion**.
2. **Зеркало удалено в v0.6.0** («вообще не интересно», его слово
   2026-11-10). Оно работало на живом ТВ с v0.4.8 (три сессии
   с картинкой: FIT/FILL/STRETCH), но в приложении его больше нет.
   Исходники — только в `build/classes.jar` сборки v0.5.2 и в DEX
   старых APK (проект без git-репозитория).
3. **Токены плеера живут часы** — извлечённая ссылка устаревает;
   при ошибке каста открыть эпизод в браузере заново и извлечь снова.
4. **Без DRM** — защищённый контент (Widevine/FairPlay) не поддерживается.
5. **targetSdk 34, не 35/36** — на ВМ есть только платформы
   android-28 и android-34; на Android 16 (realme GT 7 Pro) приложение
   работает, но targetSdk стоит поднять при наличии SDK 35/36.
6. **Подпись — тестовый ключ** (`build/aircast.keystore`), не релизный.
   Для публикации в магазине нужен свой релизный ключ.
7. **Авто-детект может не найти видео сам** — если плеер отдаёт
   manifest только после ручного нажатия ▶ (зависит от плеера):
   через 30 с появится фолбэк с видимым браузером, нажми ▶ в плеере
   сам, ссылка перехватится и видео запустится.
8. **Реальный Apple TV с этой ВМ не тестировался** — ВМ не в домашней
   сети Алексея. Все проверки против его ТВ — по шагам ниже.

## Тест для Алексея (точная последовательность, v0.6.0)

1. **Телефон и ТВ в одной домашней Wi-Fi сети**, Apple TV включён
   (не в глубоком сне), на ТВ разрешён AirPlay.
2. Установить APK по ссылке из письма/чата (разрешить установку
   из неизвестных источников для браузера/файлового менеджера).
   **Старую версию (v0.5.2) НЕ удалять — обновится поверх.**
   Критично: после обновления приложение НЕ должно спросить PIN
   Companion (спаривание и запомненный ТВ сохраняются). Если
   спросило — сообщить, это баг обновления.
3. **Главный флоу — share из Chrome.** Открыть в Chrome страницу
   серии (например, Rosario+Vampire на YummyAnime) → меню Chrome →
   «Поделиться» → «VLC Cast». Приложение откроется на одном экране:
   статус «Ищу видео…», затем карточка видео (720p · m3u8) и
   «Команда VLC отправлена — смотри на ТВ». Сообщить: открылся ли
   VLC на ТВ и играет ли видео. Браузер на экране телефона при этом
   НЕ виден (фоновый WebView) — это нормально.
4. **Если видео не нашлось само за 30 с** — появится фолбэк:
   видимый браузер со страницей + «Найденные видео». Нажать ▶
   в плеере на странице — ссылка перехватится, видео запустится
   само. Сообщить, сработал ли авто-детект или понадобился фолбэк.
5. **Прямая ссылка.** Поделиться из Chrome прямой ссылкой на
   .mp4/.m3u8 — должна запуститься во VLC сразу, без загрузки
   страницы.
6. **Кнопка «▶ На ТВ».** После запуска — повторный тап должен
   запустить видео заново.
7. Если что-то не так — «Диагностика и журнал» →
   «Поделиться журналом» и прислать лог вместе с тем, что видно на
   экране ТВ. Важны строки: `share: получена ссылка из Chrome`,
   `browser: найдено видео [m3u8 720p]`, `vlc: запуск OK`,
   `Companion: Pair-Verify OK`, `открываю плеер автоматически`,
   `авто-play в плеере: …`.
